Evidence as a property of the system

Kogent treats evidence as a property of the system, not an afterthought. Specifying, building, verifying and shipping a change happens in one place — so the record of why something is in production is a byproduct of the workflow rather than something assembled afterwards.

This page states what is built today and what is not. Where a capability is on the roadmap, we say so plainly rather than implying it ships.

The audit trail

Changes are recorded as append-only, attributed history — who, what, and when. The server audit logs go further: entries are hash-chained, and the chain is checkpointed on a schedule with Ed25519-signed checkpoints plus an independent witness held outside the database, so a verifier can detect after-the-fact edits rather than asking you to trust that none happened.

A compliance-retention mode exempts audit-bearing records from routine retention pruning, so the trail cannot be quietly aged out. Records outside the server audit logs — the build and artifact stores — are append-only and attributed, but are not part of the hash chain.

Evidence you can take with you

  • Evidence binder. A one-click, hash-manifested export of a release's evidence — specifications, validation history, verification results and reviews — with a manifest over the exported files and the audit chain's current checkpoint and verifier verdict embedded. It is offline-navigable and yours to keep.
  • Electronic signatures. A Part-11-shaped signing primitive is built: a review is signed with a freshly issued email challenge, producing a rendered manifest that records the signing identity. It requires a configured mail provider, and signature enforcement is off by default — a single-operator workspace cannot function with it on. We are aligned with 21 CFR Part 11; we are not a validated Part 11 package and hold no certification to it.

How AI-written changes are verified

Autonomous builds are gated by deterministic checks rather than by a model's judgement of its own work:

  • The specification is admitted by code, not a model. A build cannot start from an empty spec, one below a completeness threshold, or one with no testable criteria.
  • Tests are written first, and proven to fail first. An independent step authors an acceptance test per criterion and proves each one fails against the untouched repository.
  • The generator never sees the gates. The model that writes the change is given the specification only — not the test suite, not the gate configuration.
  • Verification runs on a pristine clone with only the candidate change applied, in a separate environment from the one that produced it.
  • A reward-hacking guard routes changes that touch tests, CI configuration, the test runner or lockfiles to a human, and fails empty changes outright.
  • A human approves before anything opens. A pull request opens only when the latest review is an approval and the run's own verdict is a pass — and it opens from the server's stored change, never a client-supplied one.
  • Coverage reports honestly. A criterion that could not be verified is reported as unverified rather than as a pass.

Every run is recorded as a replayable record, so “why did the agent do that?” is answerable after the fact.

Keys and model providers

Provider API keys are never embedded in the application and never read from its environment. They live in a server-side vault encrypted with AES-256-GCM, scoped per workspace, and are released only at the moment of use — to the model proxy for interactive calls, or into an isolated single-use sandbox for a build.

The desktop application holds no provider keys and talks to the proxy, never to model vendors directly. Inside a build sandbox the credential is not the key either: each run carries a short-lived token scoped to one workspace, one provider and one phase of the run, which the proxy exchanges for the real key on the way out and revokes when the run ends. Code running in a sandbox — including code the model just wrote — never has a credential worth stealing.

The proxy is model-neutral across Anthropic, OpenAI and Google. Every model call is metered into a usage ledger, and autonomous runs carry hard budgets on tokens, retries and wall-clock time — a run stops when it reaches its cap.

Isolated execution

Generated code is never run on your machine or in a shared environment. Each autonomous build gets a cold, single-use micro-VM sandbox with deny-by-default network egress enforced outside the virtual machine, so code running as root inside it cannot lift its own restrictions. Verification always happens on a fresh clone, so a run cannot quietly contaminate the environment that judges it.

Application security

  • A memory-safe core. Authority, inter-process validation, secret handling and system integration live in Rust. The interface layer is treated as an untrusted client of that core: every message crossing the boundary is validated, every path is canonicalised and confined to a known workspace root, and every database query uses bound parameters.
  • Signed updates. Update manifests are cryptographically verified against an embedded public key, so only releases we signed can install.
  • A hardened supply chain. Dependencies are pinned and locked; continuous integration runs secret scanning and dependency vulnerability audits across both the JavaScript and Rust trees on every push; and every release ships a software bill of materials alongside signed artifacts.

Access

Access is scoped per workspace — only the people you invite can see a workspace's data — and every request is checked against that membership before it is forwarded. Workspace membership has two tiers, and the line between them is drawn at the one operation that hands back a secret: any member can add, replace or remove a provider key, but only an owner can read a stored key back in plaintext. Every such read is written to the audit trail.

The stronger protection is structural rather than permissional: no client ever receives a provider key at all. The desktop application can only write to the vault, and model calls are made by the proxy on your behalf, so a compromised account cannot extract a credential that never reaches it.

An independent-review gate can require that the reviewer of a run is not its author, the separation-of-duties control regulated environments expect; it is opt-in.

Not yet built

Single sign-on (SAML/OIDC), SCIM provisioning and role-based access control are on the roadmap and are our current priority for enterprise deployments.

Deployment

Kogent runs single-tenant today, and can be self-hosted. A bring-your-own-cloud architecture — where the data plane runs inside your own cloud account under customer-managed encryption keys, with all connectivity initiated outbound from your environment — is the direction we are building toward; the envelope-encryption foundation is in place, the full data plane is not. We will not describe it as available until it is.

Compliance

Kogent is not currently certified to SOC 2, ISO 27001 or ISO/IEC 42001. Those certifications are on our roadmap, and we are glad to walk enterprise teams through our current posture, the evidence the product already produces, and our timeline during procurement.

Data processing

A Data Processing Agreement (DPA) is available on request for enterprise customers. Full security documentation, including our threat model and secret-rotation process, is shared under NDA during procurement.

Reporting a vulnerability

Report suspected vulnerabilities to security@kogentai.com. Please do not open public issues for security matters. We acknowledge within 72 hours.
